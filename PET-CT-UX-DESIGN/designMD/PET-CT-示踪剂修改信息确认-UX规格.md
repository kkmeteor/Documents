# UX Specification: PET-CT 示踪剂双重确认与审计系统

## Pass 1: Mental Model

**Primary user intent:** 核医学技师在PET-CT检查中安全、准确地记录放射性示踪剂注射信息，确保任何修改都经过第二人确认并留下完整审计轨迹。

**Likely misconceptions:**

- **"保存就是最终生效"** — 用户可能认为点击保存后数据立即生效，不理解需要第二人确认才能最终提交
- **"审计记录是事后查看的"** — 用户可能不知道每次修改都会实时生成审计条目，误以为审计是独立功能
- **"双重确认 = 两次保存"** — 用户可能以为自己要保存两次，不理解是两个人各做一次确认
- **"修改和首次录入流程相同"** — 用户可能以为首次录入也需要双重确认，实际上双重确认仅针对修改场景

**UX principle to reinforce/correct:** 首次录入由一人完成即可保存生效；修改已保存数据时才触发双重确认流程。系统通过明确的状态标签（"待确认"/"已确认"）和双人签名区域让用户始终清楚当前处于哪个阶段。

## Pass 2: Information Architecture

**All user-visible concepts:**

- 病人体位选择
- 核素选择（F18等）
- 示踪剂选择（FDG等）
- 满针时间 / 满针剂量
- 空针时间 / 空针剂量
- 注射时间 / 注射剂量
- 注射日期
- 保存/取消操作
- 修改确认弹窗
- 第二人确认界面
- 审计日志面板
- 数据状态标识（已确认/待确认/已修改）

**Grouped structure:**

### 基本信息区（Primary）

- 病人体位: Primary — 检查基本参数，影响后续成像
- 核素: Primary — 决定放射性同位素类型
- 示踪剂: Primary — 决定具体药物

### 注射剂量数据区（Primary）

- 满针时间/剂量: Primary — 注射前基准数据
- 空针时间/剂量: Primary — 注射后剩余数据
- 注射时间/剂量: Primary — 核心计算结果（自动计算但可手动修正）
- 注射日期: Primary — 时间戳锚点

### 操作控制区（Secondary）

- 保存按钮: Secondary — 触发保存或确认流程
- 取消按钮: Secondary — 放弃当前编辑

### 双重确认流程（Secondary → Progressive）

- 修改确认弹窗: Secondary — 仅修改时出现
- 第二人身份验证: Secondary — 仅修改时出现
- 确认/拒绝操作: Secondary — 第二人决策

### 审计追踪（Hidden → Progressive）

- 审计日志入口: Hidden — 通过图标/链接渐进展示
- 审计详情面板: Hidden — 展开后显示完整变更记录
- 修改前/后值对比: Hidden — 审计详情内展示

## Pass 3: Affordances

| Action | Visual/Interaction Signal |
|--------|--------------------------|
| 选择体位 | 下拉箭头 + 图标，标准选择器外观 |
| 选择核素/示踪剂 | 下拉箭头，标准选择器外观 |
| 编辑时间字段 | 时钟图标 + 下划线，点击弹出时间选择器 |
| 编辑剂量字段 | 下划线输入框，可直接键入数字 |
| 保存（首次录入） | 实心按钮，点击直接保存 |
| 保存（修改场景） | 实心按钮，点击触发双重确认弹窗 |
| 取消 | 线框按钮，点击放弃编辑 |
| 查看审计日志 | 时钟/文档图标按钮，点击展开审计面板 |
| 第二人确认 | 独立确认面板，含身份输入 + 确认/拒绝按钮 |
| 已确认状态标识 | 绿色勾选图标 + "已确认"标签 |
| 待确认状态标识 | 橙色警告图标 + "待第二人确认"标签 |
| 修改标记 | 字段旁显示铅笔图标或高亮边框 |

**Affordance rules:**

- 如果用户看到字段旁有绿色勾选图标，应理解为该数据已经双重确认
- 如果用户看到字段旁有橙色警告图标，应理解为该数据正在等待第二人确认
- 如果用户看到铅笔图标，应理解为该字段已被修改但尚未确认
- 如果用户点击保存时数据是首次录入，应直接保存无需额外确认
- 如果用户点击保存时数据是修改已有记录，应弹出双重确认流程

## Pass 4: Cognitive Load

**Friction points:**

| Moment | Type | Simplification |
|--------|------|----------------|
| 修改后点击保存 | Choice | 弹窗明确告知"需要第二人确认"，只需输入确认人姓名即可，不要求复杂操作 |
| 第二人确认时 | Uncertainty | 弹窗清晰展示修改前/后值对比（diff视图），确认人一目了然知道改了什么 |
| 等待确认期间 | Waiting | 原数据显示"待确认"状态标签，不锁定界面但标记未生效，其他人可继续工作 |
| 查看审计记录 | Uncertainty | 审计面板默认收起，点击图标展开；按时间倒序排列，最新修改在最上方 |
| 首次录入 vs 修改 | Uncertainty | 系统自动判断：无历史记录=首次录入（直接保存）；有历史记录=修改（触发确认） |
| 确认人身份验证 | Choice | 仅需输入工号/姓名，不要求密码（内网环境信任前提），降低操作负担 |

**Defaults introduced:**

- 注射剂量自动计算（满针剂量 - 空针剂量）: 减少手动计算错误，用户可覆盖但需确认
- 注射时间默认为空针时间: 合理默认值，减少一次输入
- 审计面板默认收起: 不干扰主操作流程，按需展开
- 确认人只需输入姓名/工号: 内网环境下不需要密码二次验证，保持操作轻量

## Pass 5: State Design

### 示踪剂信息表单

| State | User Sees | User Understands | User Can Do |
|-------|-----------|------------------|-------------|
| Empty | 所有字段为空，核素/示踪剂显示placeholder | 需要录入新的示踪剂信息 | 选择核素、示踪剂，填写各项数据 |
| Loading | 字段显示加载动画 | 正在从系统加载已有数据 | 等待加载完成 |
| Success (首次) | 所有字段已填写，显示绿色"已保存"标签 | 数据已成功保存 | 继续检查流程或修改数据 |
| Success (已确认修改) | 字段显示绿色"已确认"标签 + 第二人签名 | 修改已被第二人确认生效 | 继续检查流程 |
| Partial | 部分字段已填写 | 数据不完整，不能保存 | 继续填写剩余字段 |
| Error | 字段旁显示红色错误提示 | 输入值不合法（如剂量为负数） | 修正错误值 |

### 修改确认弹窗

| State | User Sees | User Understands | User Can Do |
|-------|-----------|------------------|-------------|
| Empty | N/A（弹窗不会以空状态出现） | — | — |
| Loading | 弹窗显示"正在加载修改对比..." | 系统正在准备diff数据 | 等待 |
| Success | 显示修改前/后值对比表 + 确认人输入框 + 确认/拒绝按钮 | 需要第二人审核并决策 | 输入确认人姓名，点击确认或拒绝 |
| Partial | 确认人姓名为空 | 必须填写确认人才能操作 | 输入确认人姓名 |
| Error | 确认人姓名无效（系统中不存在） | 输入的确认人无法识别 | 重新输入正确的确认人 |

### 审计日志面板

| State | User Sees | User Understands | User Can Do |
|-------|-----------|------------------|-------------|
| Empty | "暂无修改记录" | 该检查尚无修改历史 | 关闭面板 |
| Loading | 加载动画 | 正在获取审计记录 | 等待 |
| Success | 按时间倒序的修改记录列表 | 每次修改的完整信息 | 滚动查看、关闭面板 |
| Partial | N/A | — | — |
| Error | "无法加载审计记录" | 网络或系统异常 | 重试或关闭 |

### 数据状态标识（字段级）

| State | User Sees | User Understands | User Can Do |
|-------|-----------|------------------|-------------|
| 已确认 | 绿色勾选 + "已确认" | 数据有效且经过双重确认 | 如需修改则触发新的确认流程 |
| 待确认 | 橙色警告 + "待第二人确认" | 修改已提交但未确认 | 等待确认人或催促确认 |
| 已修改(未提交) | 铅笔图标 + 黄色高亮 | 当前编辑尚未保存 | 保存或取消 |
| 首次录入 | 无特殊标识 | 正常录入状态 | 正常填写和保存 |

## Pass 6: Flow Integrity

**Flow risks:**

| Risk | Where | Mitigation |
|------|-------|------------|
| 用户误以为修改已生效 | 修改保存后、确认前 | 字段显示"待确认"状态，数据不写入最终记录 |
| 第二人找不到待确认项 | 确认流程中 | 系统推送通知或在首页显示待确认任务列表 |
| 确认人就是修改人（自己确认自己的修改） | 确认弹窗中 | 系统校验确认人≠修改人，相同则报错提示 |
| 用户不知道有审计功能 | 整个界面 | 在示踪剂标题旁放置审计图标入口，始终可见 |
| 确认流程卡住（确认人不在场） | 待确认状态 | 允许修改人撤回修改，恢复为修改前值 |
| 多次修改产生混乱 | 连续修改场景 | 每次修改都基于最新已确认值，审计记录链式展示 |
| 首次录入被误判为修改 | 保存逻辑判断 | 系统检查是否存在历史记录，无记录则走首次录入流程 |

**Visibility decisions:**

- Must be visible: 当前数据状态（已确认/待确认）、保存/取消按钮、审计日志入口图标、修改时的确认弹窗
- Can be implied: 自动计算的注射剂量（显示计算结果即可，不需要展示公式）、审计记录的时间戳格式（标准格式用户自然理解）

**UX constraints:**

- 双重确认弹窗必须模态（modal），阻止其他操作直到确认完成
- 审计日志面板必须非模态（non-modal），不阻断主操作流程
- 确认人不能与修改人为同一人（系统强制校验）
- 修改前的原始值必须完整保留在审计记录中，不可覆盖
- 待确认状态的数据不能用于后续检查流程（如扫描参数计算）

### Interaction Flow Summary

```
首次录入流程:
  填写字段 → 点击[保存] → 直接保存 → 显示"✅ 已确认"

修改流程:
  点击[修改] → 编辑字段(黄色高亮) → 点击[提交确认]
    → 弹出双重确认弹窗(diff对比)
    → 第二人输入身份 → 点击[确认]
    → 数据生效 → 显示"✅ 已确认" + 审计记录更新
    → 或第二人点击[拒绝] → 数据回滚 → 显示原值

待确认状态:
  修改已提交 → 界面显示"️ 待第二人确认"
    → 第二人登录 → 看到确认/拒绝按钮
    → 确认后数据生效 / 拒绝后数据回滚

审计查看:
  任意状态 → 点击[审计📋] → 展开审计面板
    → 查看所有变更记录（时间倒序）
    → 点击 ✕ 关闭面板
```
