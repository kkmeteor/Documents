# 企业 RAG 知识库架构设计

> **文档版本**：V1.0 | **编制日期**：2026-06-22 | **适用系统**：SinoUnion AI Agent Studio
> 本文件合并自两份《企业RAG知识库架构设计文档》（A版：四层架构；DB版：三层架构），两份文档核心理念一致，内容去重整合。

---

## 一、背景与痛点

企业内部知识文档长期散落在多个系统中——SharePoint、Confluence、钉钉/飞书文档、TAPD、NAS 共享盘、Git Wiki、本地文件夹等，形成"信息孤岛"。主要痛点：

- 员工查找知识效率低，新入职人员学习成本高，隐性知识随人员流动流失
- **90% 以上的企业 RAG 项目采用"两套系统"**：一套给人用的 Wiki，一套单独给 AI 用的向量库，维护成本高、数据不一致、AI 回答与人类查阅内容常冲突
- 缺乏统一权限体系，存在数据安全隐患
- AI 回答无法溯源，出现幻觉难以验证和修正

## 二、核心理念与目标

### 2.1 核心理念：人机共源 / 单一源、双消费

**文档只存一份**，同时满足人类阅读和 AI 检索两类需求，而非为 AI 单独构建一套封闭知识库。文档以原始格式统一存储，人类通过前端阅读原件，AI 的向量索引从同一份文档生成，不存在"人类版本"和"AI 版本"的割裂。

### 2.2 业务目标

1. 建立企业唯一知识入口，实现内部知识统一管理与高效复用
2. 为 AI Agent 提供高质量、实时更新、权限可控的知识源
3. 降低知识获取成本，提升员工工作效率和 AI 回答准确率

### 2.3 技术目标

1. 实现"单一源、双消费"核心架构
2. 建立与现有系统完全一致的统一权限体系
3. 实现文档变更的自动增量同步与向量索引更新
4. 提供完整的 AI 回答溯源与审计能力
5. 与 SinoUnion AI Agent Studio 无缝集成

### 2.4 设计原则

| 原则 | 说明 |
|------|------|
| **人机共源（单一源）** | 所有文档只存一份原始文件，任何修改仅作用于原始文件，系统自动同步更新向量索引 |
| **适配人而非迁移人** | 通过连接器从现有系统同步文档，不要求员工改变习惯；系统去适配人的工作方式 |
| **权限优先/权限一致** | 人类不能访问的文档，AI 绝对不能检索和引用；AI 检索严格遵守与人类相同的权限控制 |
| **增量同步** | 仅同步和重新索引发生变更的内容，避免全量扫描和计算 |
| **溯源可审计** | 所有 AI 回答必须可追溯到原始文档的具体段落和版本 |
| **体验统一** | 知识库功能完全集成到现有 AI Studio 界面，无需用户切换系统 |
| **渐进式建设** | 分阶段实施，先跑通核心链路再逐步扩展 |

## 三、整体架构

两份文档分别采用四层与三层架构，本质一致，综合如下：

```
┌────────────────────────────────────────────────────────────────────┐
│                        消费服务层                                    │
│  ┌─────────────────────────┐         ┌──────────────────────────┐  │
│  │   人类访问门户            │         │   AI 消费端               │  │
│  │ 浏览/搜索/协作/版本管理    │         │  RAG检索API / Agent接口   │  │
│  │ 评论/收藏/分享/摘要       │         │  知识库配置 / 检索日志统计  │  │
│  └──────────┬──────────────┘         └───────────┬──────────────┘  │
├─────────────┼────────────────────────────────────┼─────────────────┤
│             │          索 引 层                   │                 │
│  ┌──────────▼───────────┐       ┌───────────────▼─────────────┐   │
│  │  全文索引 Elasticsearch│       │ 向量索引 Milvus / Qdrant     │   │
│  └──────────┬───────────┘       └───────────────┬─────────────┘   │
├─────────────┼────────────────────────────────────┼─────────────────┤
│             │          处理层（核心处理引擎）        │                 │
│  ┌──────────▼────────────────────────────────────▼─────────────┐   │
│  │  格式解析 → 智能分块 → Embedding → 索引写入                    │   │
│  │  敏感内容检测 | 元数据提取 | 变更同步引擎 | 质量评分引擎         │   │
│  └────────────────────────┬─────────────────────────────────────┘   │
├───────────────────────────┼────────────────────────────────────────┤
│                           │        存储层（核心知识库层）            │
│  ┌────────────────────────▼─────────────────────────────────────┐   │
│  │  原始文档库(对象存储 MinIO) | 元数据与权限库(PostgreSQL)        │   │
│  └─────────────────────────────────────────────────────────────┘   │
├────────────────────────────────────────────────────────────────────┤
│                        数据源接入层                                  │
│  钉钉/飞书 | Confluence | GitLab/GitHub | SharePoint | 企业网盘    │
│  邮件系统 | Jira/禅道 | CRM | ERP | TFS | 本地文件 | 批量导入      │
└────────────────────────────────────────────────────────────────────┘
```

### 3.1 存储层 — 文档原仓（原始文档库）

- **存储选型**：MinIO（自建对象存储，S3 兼容，适合内网、数据不出域）或阿里云 OSS（已使用阿里云生态的团队）
- **元数据库**：PostgreSQL，存储文档元信息（标题、来源、作者、时间、所属知识库、权限标签、处理状态），与对象存储文件通过 URI 关联
- 保留完整文档版本历史，支持版本对比和回滚
- 目录按知识库（Knowledge Base）顶层分区，其下按来源或业务域划分子目录

### 3.2 处理层 — 文档处理流水线

文档入库后自动触发处理流水线，依次经过：**格式解析 → 智能分块 → Embedding → 索引写入**。

- **格式解析**：PDF（含 OCR）、Word/Excel、Markdown/HTML、代码文件等转为结构化文本（保留标题层级、段落、表格、列表结构标记）
- **智能分块**：按文档类型选择不同策略（详见第五节），每个 chunk 保留与原文档的关联（doc_id、chunk_index、页码/章节定位）
- **Embedding 生成**：对每个 chunk 生成向量，推荐 BGE-M3 或 text-embedding-v3（支持中英文），维度通常 1024 或 1536
- **索引写入**：chunk 文本写全文索引，向量写向量库，权限标签/文档类型/来源等元数据一并写入

### 3.3 索引层 — 双索引并存

- **向量索引**（Milvus / Qdrant）：服务 AI Agent 语义检索，支持 top-k 相似度、metadata 过滤
- **全文索引**（Elasticsearch）：服务人类关键词搜索，精确匹配、模糊搜索、高亮
- **混合检索（Hybrid Search）**：同时查询两个索引，通过 RRF（Reciprocal Rank Fusion）或加权融合合并结果，效果显著优于纯向量检索（尤其专有术语、产品型号等精确匹配场景）

### 3.4 服务层 — 统一入口

**人类访问门户**：Web 界面，知识库浏览、文档搜索（关键词+语义）、在线阅读/下载、评论/收藏/标注、知识库管理；搜索定位到具体 chunk，点击跳转原文并高亮。

**AI 消费端**：RAG 检索 API（输入 query 返回 top-k chunks + metadata + 原文链接）、知识库列表与元信息查询、文档详情获取、Agent 集成接口、溯源机制（检索结果含原始文档 ID、版本号、段落号和原文片段）。

> 两个入口查询的是**同一份文档、同一套索引**，只是呈现方式不同。

## 四、文档收集策略与数据源接入

### 4.1 三步走策略（优先被动同步，避免依赖员工主动上传）

**第一阶段：对接已有系统（连接器模式）**——通过预置连接器定期同步，不要求员工改变习惯：

| 优先级 | 数据源 | 对接方式 | 预期文档量 |
|--------|--------|----------|-----------|
| P0 | 钉钉/飞书文档 | 开放平台 API | 高 |
| P0 | Git 仓库 Wiki / README | Git webhook + 定时拉取 | 中 |
| P1 | Confluence / Wiki | REST API 全量 + 增量同步 | 中 |
| P1 | SharePoint / OneDrive | Microsoft Graph API | 高 |
| P2 | NAS / 文件服务器 | 文件系统监听 + 定时扫描 | 中 |
| P2 | TFS / 代码文档 | TFS API + 变更集关联 | 低 |

每个连接器需实现：增量同步（只处理变更）、格式转换、元数据提取、异常处理与重试。统一变更检测机制基于**文件哈希 + 最后修改时间 + 内容指纹**。

**第二阶段：建立知识入湖标准管道**——API 入库（业务系统通过 webhook 自动推送）、SDK/插件（Word 插件、浏览器书签栏工具一键保存）、手动上传（拖拽，补充手段）。

**第三阶段：质量治理与持续运营**——知识库 Owner 制度、过期检测、贡献统计。

### 4.2 数据源同步触发机制

| 数据源类型 | 对接方式 | 同步触发机制 | 同步粒度 |
|-----------|---------|-------------|---------|
| 在线文档系统 | 官方 API | 实时推送（保存/修改事件） | 单文档 |
| 代码仓库 | Webhook | 代码提交/Merge 事件 | 单文件 |
| 企业网盘 | API 轮询 | 增量定时同步（每 15 分钟） | 单文件 |
| 项目管理系统 | 官方 API | 需求/任务变更事件 | 单条目 |
| 会议系统 | 官方 API | 会议结束事件 | 会议纪要 |
| 邮件系统 | 邮件网关 | 特定标签邮件到达事件 | 邮件+附件 |
| 本地文件 | 桌面客户端 | 文件系统变更监控 | 单文件 |
| 历史归档 | 批量导入工具 | 手动触发 | 文件夹/ZIP 包 |

## 五、智能分块策略

Chunk 策略直接影响检索质量，推荐按文档类型差异化处理：

| 文档类型 | 推荐分块策略 | 典型 Chunk 大小 |
|----------|-------------|----------------|
| 产品手册 / 用户指南 | 按章节 / Heading 层级切分 | 500-1000 tokens |
| FAQ 文档 | 按问答对切分（Q+A 为一个 chunk） | 200-500 tokens |
| 技术方案 / 设计文档 | 按逻辑段落切分，保留上下文重叠 | 800-1500 tokens，overlap 200 |
| API 文档 | 按接口/方法切分 | 300-800 tokens |
| 代码文档 | 按函数/类/模块切分 | 按代码结构动态调整 |
| 表格密集型文档 | 表格独立成 chunk + 表头上下文 | 整表或按行分组 |
| 普通文本（DB版） | 按章节+语义分块 | 200-500 token，重叠 50-100 |
| 图片 | OCR 识别后分块 | 关联上下文信息 |

每个 chunk 携带 metadata：所属文档 ID、在原文中的位置、chunk 类型（正文/表格/代码/标题）、权限标签（继承自原文档）。建议支持**父子 chunk 关系**：命中子 chunk 时可附带父 chunk（更大范围上下文），提升回答完整性。

## 六、权限与安全模型

### 6.1 权限架构（RBAC + ABAC 混合）

- **知识库级权限**：通过角色（管理员、编辑者、查看者）管理，与 LDAP/AD 集成同步组织信息
- **文档级权限**：通过 metadata 标签控制（department、level、team），入库时携带权限标签
- **权限继承机制**：优先继承原系统权限（Confluence 页面权限、SharePoint 文件夹权限），可叠加补充但**不允许降低**原系统权限级别；权限变更自动同步

### 6.2 AI 检索的权限执行（关键安全设计）

```
用户发起查询 → 解析用户身份与权限标签 → 构造检索请求时注入 metadata 过滤条件
→ 向量检索 + 全文检索（仅返回用户有权限的 chunks）→ 结果返回
```

**核心原则**：
- 权限过滤在**检索阶段完成（pre-filtering）**，而非检索后再过滤（post-filtering）
- 每个 Agent 只能访问被明确授权的知识库
- 回答生成阶段做二次校验，防止泄露敏感信息
- 记录所有 AI 检索和回答记录，支持完整审计追溯

### 6.3 数据安全

- 传输加密（HTTPS/TLS）、存储加密（对象存储 SSE）
- 审计日志：记录所有文档访问和检索请求（谁、何时、查了什么、获取了哪些文档）
- 敏感信息过滤：处理流水线检测身份证号、银行卡号、API Key 等，高风险文档标记或自动脱敏

## 七、技术选型建议

| 组件 | 推荐方案 | 备选方案 | 说明 |
|------|---------|---------|------|
| 对象存储 | MinIO | 阿里云 OSS | MinIO 适合内网自建，S3 兼容 |
| 元数据库 | PostgreSQL | MySQL | PG 对 JSON 和向量扩展(pgvector)支持好 |
| 向量数据库 | Milvus | Qdrant / pgvector | Milvus 生态成熟，Qdrant 轻量易部署 |
| 全文检索 | Elasticsearch | Meilisearch | ES 功能全面，Meilisearch 轻量快速 |
| 文档解析 | Apache Tika + 自研 | Unstructured.io | Tika 格式覆盖广，自研补充中文优化 |
| Embedding 模型 | BGE-M3 | text-embedding-v3 | BGE-M3 开源可私有部署，支持中英文 |
| 处理流水线 | Celery + Redis | Temporal | Celery 轻量，Temporal 适合复杂编排 |
| 前端门户 | React + Ant Design | Vue + Element Plus | 与 AI Studio 现有技术栈保持一致 |

> 初期规模较小（文档量 <10 万）可简化部署：用 PostgreSQL + pgvector 同时承担元数据库和向量库，用 Meilisearch 替代 Elasticsearch，降低运维复杂度。

## 八、知识质量治理体系

1. **文档生命周期管理**：自动检测超 6 个月未更新文档标记"待更新"，向作者发送提醒，逾期自动降低检索权重；支持归档和废弃机制
2. **质量评分系统**：自动评分（更新频率、访问量、点赞数、AI 引用次数、结构完整性）+ 人工评分（准确性、实用性、完整性），低质量文档降权
3. **反馈闭环**：员工对 AI 回答评分纠错，错误回答自动标记对应文档片段提醒作者修正，系统据此优化分块策略和检索参数
4. **敏感内容治理**：入库前检测、自定义敏感词库、定期全库扫描

| 阶段 | 周期 | 核心目标 | 主要工作 |
|------|------|---------|---------|
| 一、基础框架 | 第1-4周 / DB版2周 | 跑通"上传→解析→向量化→检索问答"最小闭环 | 对象存储+元数据库；格式解析；Embedding；基础语义检索 API；RAG UI 框架；对接核心数据源 |

| 三、连接器+权限 | 第9-14周 / DB版6周 | 自动汇聚文档，权限上线 | P0/P1 连接器；RBAC+标签权限；LDAP/AD；pre-filtering；知识库 Owner；原系统权限继承 |

## 十、关键风险与应对

| 风险 | 影响 | 应对措施 |
|-----|------|---------|
| 检索质量不达预期 | 高 | 尽早建立评测数据集，持续度量 recall@k/precision@k；混合检索显著改善 |
| 数据同步延迟 | 中 | 实时推送 + 定时增量同步结合，关键系统优先实时推送 |
| 文档更新不同步 | 中 | 增量同步机制（变更时间戳/webhook）+ 手动触发重新索引 |
| 权限泄漏 | 高 | 检索层 pre-filtering 而非 post-filtering；定期权限合规审计；与原系统权限定期对比告警 |
| 权限不一致 | 高 | 建立权限校验机制，定期对比原系统权限，不一致自动告警 |
| 员工接受度低 | 中 | 从"搜索入口"切入（集成到钉钉/企业 IM 搜索框）；贡献统计正向激励；加强培训推广 |
| AI 回答质量差 | 高 | 反馈闭环 + 分块/检索优化 + 人工审核 |
| 数据安全风险 | 高 | 严格权限控制、完整审计、敏感内容检测、加密存储传输 |
