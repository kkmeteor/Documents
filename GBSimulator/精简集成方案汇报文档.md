# GBSimulator 精简集成方案汇报文档

## 一、项目背景与目标

### 1.1 现状分析
GBSimulator 项目作为 PET 采集系统的重要组成部分，承担着模拟床位数据发送的核心功能。随着业务发展，原有代码架构出现了以下问题：

- **固定床位限制**：原生仅支持固定6个床位，无法满足不同扫描场景（如心脏扫描仅需1床，全身扫描可能需要8床）
- **代码冗余**：13个文件实际功能简单，但分散在多个类中，导致代码难以追踪
- **扩展困难**：新增床位类型需要修改多处代码，违反开闭原则
- **配置管理混乱**：缺乏统一的配置加载和持久化机制

### 1.2 项目目标
通过精简集成，实现以下目标：

| 目标 | 具体指标 |
|------|----------|
| 功能增强 | 支持动态1-10床位配置，满足不同扫描场景 |
| 代码精简 | 删除13个冗余文件，减少约30%代码量 |
| 架构简化 | 移除不必要的抽象层，采用直接调用方式 |
| 维护性提升 | 统一配置管理，简化新增床位类型流程 |

## 二、设计思路演进：从固定到动态

### 2.1 原始版本（修改前）

**核心特征**：固定6床位，硬编码在UI和ViewModel中

**代码结构**：
```csharp

<TextBox Name="BedPosFilePath1" Text="{Binding ListModeDataFilePath[0]}" />
<Button Content="Select file..." Command="{Binding SelectFilePathCommand}" />

```

```csharp

private ObservableCollection<string> listModeDataFilePath =

public ObservableCollection<bool> ControlDisabled { get; set; } = 
    new ObservableCollection<bool> { true, true, true, true, true, true };

// 硬编码的6床位处理逻辑
private void SelectBedPosition_ListModeFilePath()
{
    // 只能处理固定的6个床位
    for (int i = 0; i < 6; i++) { ... }
}
```

**原始版本问题分析**：

| 问题 | 影响 |
|------|------|
| 床位数量硬编码 | 无法支持心脏扫描（1床）、儿科（4床）、全身（6-8床）等不同场景 |
| UI重复代码 | 6组相同的Label/TextBox/Button，维护困难 |
| 缺乏配置持久化 | 每次启动需重新配置，无法保存常用设置 |
| 无预设场景 | 用户需手动配置每个床位，操作繁琐 |
| 扩展困难 | 新增床位需要修改UI、ViewModel、逻辑多处 |

### 2.2 第一版设计方案（过度设计）

**设计思路**：采用完整的企业级架构模式，强调可扩展性和模块化

**文件规模**：计划新增15+个文件，总计约3500行代码

**架构特点**：
```
GBSimulatorViewModel
    ├── GBSimulatorViewModelAdapter (适配器层)
    │       └── EnhancedBedViewModel (增强ViewModel)
    │               └── DynamicBedViewModel (动态床位)
    ├── ConfigurationService (配置服务层)
    │       ├── IConfigurationLoader (配置加载接口)
    │       ├── JsonConfigurationLoader
    │       ├── XmlConfigurationLoader
    │       └── ConfigurationFactory
    ├── RuleEngineManager (规则引擎管理层)
    │       ├── IRuleEngine (规则引擎接口)
    │       ├── RuleEngine (规则引擎实现)
    │       ├── IRule (规则接口)
    │       ├── AdultWholeBodyRule
    │       ├── AdultCardiacRule
    │       ├── AdultBrainRule
    │       ├── PediatricRule
    │       └── PhantomRule
    └── PresetDataManager (预设数据管理)
            ├── 预设数据加载/保存
            ├── 数据完整性验证
            └── 自动匹配逻辑
```

**第一版方案评估**：

| 优点 | 缺点 |
|------|------|
| 高度模块化 | 过度设计，增加不必要的复杂度 |
| 规则引擎灵活 | 仅用于简单的预设匹配，大材小用 |
| 配置加载支持多格式 | 实际只需要JSON格式 |
| 完整的接口定义 | 接口过多，实现成本高于收益 |

**核心问题**：为简单的动态床位需求引入了完整的规则引擎和配置管理框架，复杂度与收益不成正比。

### 2.3 最终精简方案（实用主义）

**设计思路**：以实用为导向，删除过度抽象，保留核心功能

**文件规模**：仅需5个核心文件，总计约1500行代码

**架构特点**：
```
GBSimulatorViewModel (直接管理)
    └── DynamicBedViewModel
            ├── ObservableCollection<BedViewModel>
            ├── BedConfiguration (统一配置)
            └── ApplyPreset() (简单switch方法替代规则引擎)
```

### 2.4 三版本对比

| 维度 | 原始版本 | 第一版方案 | 最终方案 |
|------|----------|------------|----------|
| **床位数量** | 固定6床 | 动态1-10床 | 动态1-10床 |
| **代码文件数** | ~20个 | ~35个 (+15) | ~27个 (+7) |
| **代码行数** | ~2500行 | ~6000行 | ~3500行 |
| **架构复杂度** | 简单但僵化 | 过度复杂 | 简洁灵活 |
| **配置持久化** | ❌ 无 | ✅ 完整 | ✅ JSON |
| **预设场景** | ❌ 无 | ✅ 规则引擎 | ✅ Switch方法 |
| **维护难度** | 中（硬编码） | 高（多层抽象） | 低（直接清晰） |
| **扩展性** | 差 | 好但过度 | 好且实用 |

### 2.5 关键设计决策演进

#### 决策1：床位管理方式

**原始版本**：无配置加载功能

```csharp
public class JsonConfigurationLoader : IConfigurationLoader { ... }
public class XmlConfigurationLoader : IConfigurationLoader { ... }
```

**最终方案**：

```csharp
{
    var json = File.ReadAllText(filePath);
    var config = JsonConvert.DeserializeObject<List<BedConfiguration>>(json);
    InitializeFromBeds(config);
}
```

### 2.6 设计原则总结

**从原始版本到第一版的演进**：
- 解决了固定床位的限制问题
- 但引入了过度设计，增加了不必要的复杂度
- 规则引擎、配置工厂等对于简单需求过于复杂

**从第一版到最终版的演进**：
- 保留了动态床位的核心功能
- 删除了过度抽象层（适配器、规则引擎、配置工厂）
- 采用实用主义：用简单的方法实现同样的功能

**核心设计原则**：
1. **KISS原则**：保持简单直接，代码即文档
2. **YAGNI原则**：不实现当前不需要的功能
3. **实用主义**：以实际需求为导向，不预设未来扩展
4. **成本收益平衡**：复杂度增加必须有相应的收益支撑

## 三、技术方案概述

### 3.1 核心架构调整

#### 调整前架构（固定6床）
```
MainWindow.xaml (固定6床位UI)
    └── GBSimulatorViewModel
            ├── ListModeDataFilePath[6] (固定6个路径)
            ├── ControlDisabled[6] (固定6个状态)
            └── SelectBedPosition_ListModeFilePath() (硬编码6床位逻辑)
```

#### 调整后架构（动态床位）
```
MainWindow.xaml (DynamicBedControl)
    └── GBSimulatorViewModel
            └── DynamicBedViewModel
                    ├── ObservableCollection<BedViewModel> (动态床位列表)
                    ├── BedConfiguration (统一配置)
                    ├── ApplyPreset() (预设场景)
                    └── Load/Save JSON (配置持久化)
```

### 3.2 关键技术决策

| 决策项 | 原方案 | 新方案 | 理由 |
|--------|--------|--------|------|
| **床位管理** | 固定6床位硬编码 | DynamicBedViewModel动态管理 | 支持1-10床灵活配置 |
| **UI实现** | 重复6组控件 | ItemsControl动态生成 | 减少重复代码，支持动态数量 |
| **预设场景** | 无 | ApplyPreset方法 | 快速配置常见扫描场景 |
| **配置持久化** | 无 | JSON序列化 | 保存/加载常用配置 |
| **事件通信** | 直接调用 | SelectFileRequested事件 | 解耦床位选择逻辑 |

### 3.3 核心组件说明

#### 3.3.1 DynamicBedViewModel
动态床位管理的核心ViewModel，负责：
- 动态创建/删除床位
- 预设场景应用
- 配置文件的加载/保存
- 床位文件选择事件转发

#### 3.3.2 BedConfiguration
统一配置模型：
```csharp
public class BedConfiguration
{
    public int BedId { get; set; }
    public string BedName { get; set; }
    public string FilePath { get; set; }
    public bool IsEnabled { get; set; }
    public int SliceCount { get; set; }
    public double BedPosition { get; set; }
}
```

#### 3.3.3 GBSimulatorViewModel适配
- 删除 `_bedAdapter` 依赖
- 直接引用 `DynamicBedViewModel`
- 添加兼容性属性映射（保持原有接口不变）
- 订阅 `SelectFileRequested` 事件

## 七、总结

本次精简集成方案成功实现了：

1. **功能目标**：从固定6床位升级为动态1-10床位，支持5种预设场景
2. **架构优化**：删除13个冗余文件，移除过度抽象层，代码更简洁
3. **设计演进**：从过度设计的第一版方案，演进为实用主义的最终方案
4. **核心价值**：在增强功能的同时保持代码简洁，实现功能与复杂度的最佳平衡

通过对比原始版本、第一版方案和最终方案，我们找到了功能增强与代码简洁之间的最佳平衡点，为后续功能扩展奠定了良好基础。
